# Rithmic adapter

An OpenCharts adapter for [Rithmic](https://www.rithmic.com/) R|Protocol. It runs
entirely in the browser: it opens one WebSocket per Rithmic plant, logs in on each,
and maps protobuf messages onto the `OpenChartsAdapter` contract in
[`src/adapter/types.ts`](../adapter/types.ts).

## Run it

```bash
VITE_ADAPTER=rithmic npm run dev
```

The app opens on a sign-in screen:

1. Pick the **gateway** from the list of Rithmic R|Protocol locations (Chicago,
   Frankfurt, Sao Paulo, ..., `RITHMIC_GATEWAYS` in `config.ts`). It defaults
   to Test, `wss://rituz00100.rithmic.com:443`.
2. The **system** list is fetched from the gateway whenever you pick one, e.g.
   "Rithmic Test" or "Rithmic Paper Trading".
3. Enter your **user** and **password**.

The password is held only by the live session, which needs it to log in again after
a dropped connection. It is never written to storage. "Remember" stores only the
gateway, system and user.

### Environment variables

| Variable | Default | Purpose |
| --- | --- | --- |
| `VITE_ADAPTER` | – | Set to `rithmic` to boot this adapter. |
| `VITE_RITHMIC_GATEWAY` | `wss://rituz00100.rithmic.com:443` | Gateway preselected on the sign-in screen. A URL outside the list shows as "Custom". |
| `VITE_RITHMIC_APP_NAME` / `VITE_RITHMIC_APP_VERSION` | `OpenCharts` / `0.3.0` | Sent at login. **Production systems only accept an app name that passed Rithmic conformance.** The test system accepts any name. |
| `VITE_RITHMIC_PRODUCTS` | ES, MES, NQ, MNQ (CME) | `PRODUCT:EXCHANGE` list shown in the terminal. |
| `VITE_RITHMIC_CONTRACTS` | – | Pins the manual contracts, e.g. `ES:ESH7,MES:MESH7`. |

### Contract mapping

The Rithmic test system does not answer `RequestFrontMonthContract` (113), so ES,
MES, NQ and MNQ are mapped locally (`MANUAL_CONTRACTS` in `config.ts`):

| Product | Tick | Point value |
| --- | --- | --- |
| ES | 0.25 | $50 |
| MES | 0.25 | $5 |
| NQ | 0.25 | $20 |
| MNQ | 0.25 | $2 |

The contract is the current quarterly one (H/M/U/Z, one-digit year, e.g. `ESZ6`).
It rolls to the next quarter 8 days before the third Friday of the expiry month,
which is CME's equity-index roll date. Set `VITE_RITHMIC_CONTRACTS` to pin a
different one.

Tick size and point value still come from `RequestReferenceData` (14) when the
system answers it; the table is the fallback. Any other product in
`VITE_RITHMIC_PRODUCTS` is resolved through the front-month request.

In Rithmic builds, the production CSP adds `wss://*.rithmic.com` and the
`VITE_RITHMIC_GATEWAY` origin to `connect-src`.

### Use it in your own app

```ts
import { createRithmicAdapter } from "./rithmic/adapter.ts";
import { getRithmicConfig } from "./rithmic/config.ts";
import { RithmicSession } from "./rithmic/session.ts";

const config = getRithmicConfig();
const session = new RithmicSession({ config, credentials: { user, password, systemName } });
await session.connect(); // throws with Rithmic's message on bad credentials
const adapter = createRithmicAdapter({ session, products: config.products });

<OpenChartsProvider adapter={adapter}><Terminal /></OpenChartsProvider>;
// later: adapter.dispose() logs out of every plant
```

## Layout

| File | Role |
| --- | --- |
| `proto/` | The R|Protocol `.proto` files from the Rithmic SDK (v5.42), used as the source of truth. |
| `samples/` | The SDK's Node.js and Python samples, kept for reference. Not built or linted. |
| `generated/rti.{js,d.ts}` | Typed protobuf codec, generated by `npm run gen:rithmic` (`scripts/gen-rithmic.mjs`). Committed. Regenerate it after updating `proto/`. |
| `templates.ts` | Template IDs and the inbound decoder table. |
| `codec.ts` | Frame encode/decode and `RithmicError`. |
| `connection.ts` | `RithmicPlantConnection` (details below) and `listRithmicSystems`. |
| `session.ts` | `RithmicSession`: the ticker, history, order and PnL plants of one signed-in user. |
| `symbols.ts` | Front-month and reference-data resolution, and `Symbol` mapping. |
| `marketData.ts` | `MarketDataSource`: historical bars, BBO ticks, and bars built from trades. |
| `orders.ts` | Pure mappers for orders, positions, accounts and bracket ticks. |
| `trading.ts` | `TradingGateway`: accounts, orders, positions and events. |
| `simulator.ts` | The local "Simulator" paper-trading account. |
| `combinedTrading.ts` | One `TradingGateway` over the Rithmic accounts and the simulator. |
| `adapter.ts` | `createRithmicAdapter`. |
| `ui/RithmicApp.tsx` | Sign-in screen and session bar (with "Reset simulator"). |

### Simulator account

Next to the Rithmic accounts, the account selector offers **Simulator**: paper
trading on the live Rithmic quotes, executed in the browser. Nothing is sent to
Rithmic.

- **Starting state:** $50,000, no commission, no margin, whole contracts.
- **Positions:** one netted position per contract. P&L is the price move ×
  contracts × point value.
- **Market fills:** a market order fills at the ask (buy) or the bid (sell).
- **Limit and stop orders:** a limit fills at its price once the market reaches
  it. A stop triggers there and fills at the market.
- **Take profit / stop loss:** TP/SL on a position close it the same way.
- **Storage:** the state is kept in localStorage under
  `rithmic:<user>:simulator`, so it survives a reload.
- **Reset:** "Reset simulator" in the session bar starts it over.
- **Routing:** order and position ids start with `SIM:`, which is how the
  combined gateway routes cancels, modifies and closes.
- **Disabling it:** pass `simulator: false` to `createRithmicAdapter` to leave
  it out.

`RithmicPlantConnection` handles one plant:
- It logs in.
- It sends heartbeats at the interval Rithmic returns.
- It matches each reply to its request through `user_msg`.
- It reconnects with backoff and logs in again.

## How the contract maps to R|Protocol

| OpenCharts | R|Protocol |
| --- | --- |
| `getSymbols` | The manual contract map (ES/MES/NQ/MNQ), or `RequestFrontMonthContract` (113) for other products, then `RequestReferenceData` (14) for tick size, point value and description. |
| `getCandles` | `RequestTimeBarReplay` (202) on the history plant. It requests minute bars with period 1/5/15/30/60/240, or daily/weekly bars, with `direction=LAST` and `user_max_count=limit`. A truncated replay continues with `RequestResumeBars` (210). |
| live `tick` | `RequestMarketDataUpdate` (100) with `LAST_TRADE \| BBO`. Each `BestBidOffer` (151) becomes a tick. |
| live `candle` | The forming bar is updated from each `LastTrade` (150), separately for every charted timeframe. |
| `subscribeDepth` (DOM panel) | `RequestMarketDataUpdate` (100) with `ORDER_BOOK` for the symbol on screen. `OrderBook` (156) frames build an aggregated book: a snapshot image replaces it, updates set a level's size (0 removes it), and `BEGIN`/`MIDDLE`/`END` groups publish once at `END`. |
| `getAccounts` | `RequestLoginInfo` (300) and `RequestAccountList` (302). Balances come from `AccountPnLPositionUpdate` (451). |
| `getOrders` | `RequestSubscribeForOrderUpdates` (308) and `RequestShowOrders` (320). The cache is kept current by order notifications 351 and 352. |
| `getPositions` | `RequestPnLPositionUpdates` (400) and `RequestPnLPositionSnapshot` (402). Positions come from `InstrumentPnLPositionUpdate` (450), one net position per account and contract. |
| `placeOrder` | `RequestNewOrder` (312) on the account's trade route (310). With TP/SL it becomes `RequestBracketOrder` (330), with target and stop in ticks from the entry. A market order's entry is the current bid or ask. |
| `modifyOrder` | `RequestModifyOrder` (314), which waits for `MODIFIED` or `MODIFICATION_FAILED`. |
| `cancelOrder` / `cancelAllOrders` | `RequestCancelOrder` (316) / `RequestCancelAllOrders` (346). |
| `closePosition` | Full close: `RequestExitPosition` (3504), then cancels the leftover bracket legs. Partial close: an opposite market order. |
| `modifyPosition` | Moves the working target or stop leg with `RequestModifyOrder`. |

## Known limitations and things to verify on a live system

- **Template IDs.** The `.proto` files do not carry template IDs. Those marked `✔` in
  `templates.ts` are confirmed by the SDK samples. The others come from the
  R|Protocol Reference Guide; check them against the guide that matches your SDK.
- **Bar timestamps.** `BAR_MARKER_IS_CLOSE_TIME` in `marketData.ts` assumes a time
  bar's `marker` is its open time. If live bars land one period late on the chart,
  set it to `true`.
- **Position TP/SL.** It can only be moved or removed when the position came from a
  bracket order. The adapter does not attach new standalone TP/SL orders to a
  position, because two independent orders are not OCO and could open a new position.
- **Partial close and brackets.** A partial close leaves the bracket legs at their
  original size.
- **Closed positions.** `getClosedPositions` returns an empty page. There is no
  history yet.
- **Contract rolls.** The symbol list holds the contracts resolved at sign-in.
  Sign in again after a roll. The manual roll rule assumes equity-index quarterly
  contracts; only use it for ES/MES/NQ/MNQ.
- **Gateway access.** The test gateway accepts browser WebSocket connections; the
  system list loads from the sign-in screen. If a production gateway refuses
  browser origins, put a WebSocket relay in front of it and set
  `VITE_RITHMIC_GATEWAY` to the relay.

## Tests

```bash
npx vitest run src/rithmic
```

The tests run against a fake gateway (`__tests__/fakeRithmic.ts`) that decodes
requests and answers with real protobuf frames. They include the shared adapter
conformance suite.

To run the same suite against a real Rithmic system (market data only, no orders):

```bash
OC_LIVE_TESTS=1 RITHMIC_USER=... RITHMIC_PASSWORD=... RITHMIC_SYSTEM="Rithmic Test" npx vitest run rithmic-live
```
